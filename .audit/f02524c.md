## Findings and fixes

### 1. Dispatch-injected Cursor rule deleted again (fixed)

`04dbb37` (Task 86 delivery) deleted `.cursor/rules/harness-operational.mdc`,
so it is absent from `main`. This is the **third** occurrence of the same
deletion — `c395a35` and `b0fb662` each restored it after an earlier delivery
commit dropped it. Restored from `04dbb37^`. Filed as **Task 130** to settle
the underlying ownership question so the fourth occurrence cannot happen
silently.

### 2. `MPP.Methods.Tempo.ProofSignature` dropped from the module map (fixed)

`bf1381c`, while adding the two new EVM modules to the module map, rewrote the
`@moduledoc false` internals paragraph in CLAUDE.md and AGENTS.md and lost
`ProofSignature` from the `MPP.Methods.Tempo.{...}` brace group.
`lib/mpp/methods/tempo/proof_signature.ex` still exists and is used by
`MPP.Methods.Tempo.Proof`. That paragraph exists specifically "so a
gap-analysis pass doesn't re-file them as missing", so the omission actively
misleads. Restored in both files. Filed as **Task 129** — this is the second
module-map drift in one range and belongs in CI, not in an audit's hands.

### 3. README MCP paragraph deleted as collateral (fixed)

`bf1381c` also deleted the "For a hand-written MCP server…" paragraph
documenting `MPP.Mcp.payment_required_error/1`,
`MPP.Mcp.verification_failed_error/2`, and the full `MPP.Mcp.error_code/1`
problem→code mapping. That paragraph was added by Task 124 (`0852bf3`); all
three functions still exist and are public (`lib/mpp/mcp.ex:153,316,354`).
Nothing in that commit's stated purpose — pinning the EVM broadcast hash —
touches MCP. Restored verbatim.

### 4. `docs/evm-permit2.md` orphaned (fixed)

The same rewrite dropped the README sentence linking to
`docs/evm-permit2.md`. After the range, that document — the full Permit2
configuration and signing walkthrough — was reachable from no link in
README.md, CLAUDE.md, AGENTS.md, or any other doc. Restored the link.

### 5. CHANGELOG gap for the new EVM credential type (fixed)

Task 86 added a whole new credential type and a new public module
(`MPP.Methods.EVM.Transaction`) with no `[Unreleased] → Added` entry; only the
keccak dependency change was recorded. The comparable Stellar and Permit2
features each have one. Added an entry covering the validation set, the
broadcast-hash pinning, the `Transfer`-log requirement, and Task 128's
acceptance gating.

### 6. Split detection in `EVM.Transaction` diverged from the rest of the method (fixed)

`MPP.Methods.EVM.Transaction.splits?/1` keyed on `is_list(splits) and splits != []`,
while every other split gate in the method keys on presence —
`MPP.Methods.EVM.reject_splits/2:428` and `advertised_credential_types/1:312`
both use `Map.has_key?(config, "splits")`. Failure: with
`method_details` of `%{"transaction" => true, "splits" => []}` (or a malformed
non-list `"splits"`), `advertised_credential_types/1` zeroes the type list for
`hash` and `authorization`, then `Transaction.offered?/1` returns true and
re-inserts `"transaction"`, and `validate/2` accepts the credential —
`transaction` becomes the single type that slips through a split config that
every other path refuses. `MPP.Methods.EVM.Permit2` independently rejects an
empty `"splits"` key (`permit2.ex:202`), so the degenerate config has no
consistent owner.

Not a settlement-safety hole (the transfer is still pinned to the charge's
chain, token, recipient and exact amount), but it breaks the invariant the
`f300bb0` audit established for this method. Changed `splits?/1` to
`Map.has_key?/2` with a comment naming the two call sites it now matches, and
added tests on both `offered?/1` + `challenge_method_details/1` and
`validate/2` for the empty and malformed cases.
