## Findings

### 1. Authorization credentials bypassed the Permit2 splits guard (serious) — FIXED

`MPP.Methods.EVM.verify/2` guarded the `hash` branch with `reject_hash_splits/1`
but left the `type="authorization"` (EIP-3009) branch ungated. On a split charge
an unsolicited authorization credential would settle the **full** charge amount to
the primary recipient and pay **no** split leg, while the server accepted the
payment and released the resource.

Advertising was already correct (`Authorization.offered?/1` returns false when
splits are configured, and `advertised_credential_types/1` narrows a split charge
to `["permit2"]`), and `docs/evm-permit2.md` already asserted the behaviour —
*"Split challenges advertise only Permit2; hash and EIP-3009 credentials cannot
fulfill them."* The code enforced half of that sentence. Advertising is not
enforcement: a client chooses its own payload type.

Fixed by generalizing the guard to `reject_splits/2` and calling it from both
branches, with a comment naming the failure it prevents. Test added to
`test/mpp/methods/evm_permit2_test.exs` alongside the existing hash assertion.

`lib/mpp/methods/evm.ex` is inside the mutation campaign's fingerprint set, so
the edit tripped `security_campaign_test.exs` (`:fingerprint_mismatch`) and with
it `mix ci`. The fingerprint was refreshed **after** re-running the executable
campaign (`mix mutation.security`) against the edited source, not instead of it —
every mutant, including the three canaries, was re-confirmed killed. This is the
third fingerprint refresh in the range (`2fbbd33`, `690d3d3` are the other two);
refreshing without re-running would silently re-ratify a stale verdict.

### 5. Per-module coverage under the critical-tier floor (moderate) — FILED as Task 127

Cold `mix ci` reports a green aggregate of **95.98%** while three Stellar modules
sit far below the repo's 95% critical-tier floor: `Stellar.RPC` 71.60%,
`Stellar.Envelope` 73.91%, `Stellar` 86.96%. Task 126 (already filed by `a4bd047`)
raises those three — but nothing stops the next method from landing the same way.
This is the whole-surface class from `CLAUDE.md` § *Domain & Whole-Surface Defects*:
the aggregate threshold structurally cannot express the invariant, so no per-task
reviewer gets a signal.

Filed **Task 127** for the class (not another instance): gate per-module coverage
for `lib/mpp/methods/` off the coverage JSON the gate already produces, with an
absolute uncovered-line allowance for behaviour-sized modules, and raise the two
non-Stellar modules below the floor (`XRPL.Wallet` 82.35%, `Tempo.HostedFeePayer`
89.74%). Depends on 126.

The modules the range itself introduced are all above the floor:
`EVM.Permit2` 98.83%, `EVM.Permit2.Settlement` 100%, `Tempo.ProofSignature` 96.67%,
`Mcp` 100%, `Client.Transport.HTTP` 100%.

## Reviewed and deliberately not changed

- **`IO.puts` in two new `:integration` tests** (`evm_permit2_integration_test.exs:94`,
  `p256_proof_integration_test.exs:77`). Off the pattern of the repo's other
  integration tests, but both print a live on-chain reference (settlement tx hash,
  Moderato access-key / authorization hash) that is the useful artifact of a live
  run. Kept.
- **`MPP.Methods.Tempo.Proof.recover_authorized_proof_signer/3`** has no `lib/`
  caller after Task 107 moved production code to `recover_authorized_proof_key/3`;
  it is now a thin wrapper exercised only by tests. It is a documented public
  function on a publicly-mapped module, so removing it is a breaking change, not
  hygiene. Left as-is.
- **`Map.get(config, "poll_timeout_ms", 60_000)` still inlined at
  `lib/mpp/methods/xrpl.ex:358,376`** while `RPC.timeout/1` now delegates to
  `Shared.poll_timeout_ms/1`. Not duplication worth collapsing: both call sites
  *validate* the raw config value (`is_integer/1` and `> 0`), which the
  `pos_integer()`-returning helper would defeat.
- **`crc` → `elixir_make` arriving transitively via `stellar_base`** adds a native
  compile step to a library's dependency tree. It is a consequence of the
  documented `stellar_sdk`-avoidance decision (`mix.exs`: hackney ~> 1.17 is
  unpatched for EEF-CVE-2026-47071), and it built clean from cold here. Noted, not
  a finding.
