## Findings

### 1. CHANGELOG gap for both deliveries — **fixed**

Neither task 100 nor task 106 wrote a `[Unreleased]` entry, and both are
user-visible: 106 changes the JSON-RPC error codes a server emits *and* the
client's retry semantics (it will now pay a second time on a `-32043` that
carries challenges — a wallet-spending behavior change); 100 adds new route
options. `CLAUDE.md` § "Always Update Project Documentation" makes this
mandatory. Added `### Added` and `### Changed` blocks under `[Unreleased]`,
including the explicit two-attempt bound and the reason for diverging from
mppx's `maxPaymentAttempts = 3`.

### 2. `CLAUDE.md` / `AGENTS.md` module map stale in three places — **fixed**

Both deliveries updated the README module table and left the `CLAUDE.md` module
map behind:

- `MPP.Mcp` — constants listed as `-32042/-32602/-32043`; `-32603` and
  `error_code/1` were missing.
- `MPP.Client.MCP` — described as "single retry"; it is now at most two payment
  attempts.
- `MPP.Discovery.OpenApi` — no mention of route parameters or response schemas.

Applied the same three edits to `AGENTS.md`, which cross-family reviewers read
instead of `CLAUDE.md`. Note that `mix agents.check` **skipped** in this tree
(`sync-agents-md.sh` is a developer-host script, absent here), so the sync was
done by hand rather than by the renderer — worth a glance from the next session
that runs on the developer host.

### 3. `OpenApiSpex.OpenApi.from_map/1` described as a validator — **fixed**

`test/mpp/discovery/open_api_test.exs` labelled its `open_api_spex` call an
"Independent validator". `from_map/1` decodes; it does not schema-validate and
will not reject a malformed document. The test's real signal is the
per-assertion navigation of `spec.paths[...].get.parameters`, which does prove
our output lands on the typed struct a 3.1 consumer reads. Corrected the comment
so a later reader does not over-trust the check — the tier-2 ground-truth rule
in `CLAUDE.md` depends on knowing exactly how strong the independent check is.

### 4. `MPP.Mcp.verification_failed_error/2` bypasses `error_code/1` — **filed as Task 124**

Task 106 lifted the per-transport code selection into `MPP.Mcp.error_code/1` and
converted `MPP.Transports.JsonRpc.Adapter` (hence `MPP.Mcp.call/3`). It did not
convert `verification_failed_error/2`, which still writes
`@verification_failed_code` unconditionally for whatever problem it receives.

That helper is public, is listed under "Server Helpers" in the `MPP.Mcp`
`@moduledoc`, and is unused inside this library — so its only callers are
consumers hand-rolling an MCP server. One handed `Errors.new(:invalid_payload,
...)` emits `-32043` while the built-in adapter emits `-32602` for the identical
problem: two conformance answers from one module, and nothing in the suite
notices because the library never calls it.

Not fixed inline: choosing between delegate / deprecate / generalize is a public
API decision, and the `message` string ("Payment Verification Failed") would be
wrong for a `-32602` payload either way.

**Filed Task 124** (phase 11, bundle `mcp`, `codex` / `gpt-6-astra`). Filed as
the *class* rather than this instance, per the DD-8 sibling check against 106 —
the acceptance criteria ask for an invariant test (for every
`MPP.Errors.types/0` problem, every public error-map builder's code equals
`MPP.Mcp.error_code(problem)`) so the next helper cannot drift the same way.
Folded in the related coupling: `error_code/1` matches problem URIs as literal
strings while `MPP.Errors` builds them as `@base_uri <> suffix`, so a suffix edit
silently demotes a problem to the `-32043` fallback with no compile or test
failure.

## Considered, not filed

- **`rechallenge?/1` is not on the `MPP.Client.Transport` behaviour** while
  `payment_required?/1` is. `MPP.Client.MCP` calls it module-qualified on
  `MPP.Client.Transport.MCP`, and `-32043` is MCP/JSON-RPC-specific, so the
  asymmetry is correct rather than an omission.
- **`:internal_payment_error` has no producer in `lib/`.** It exists for
  `MPP.Method` implementations to return, and `:settlement_unavailable` (503)
  already covers backend unavailability for the built-in methods. Not dead code.
- **`open_api_spex` absent from the dependency list in `CLAUDE.md`.** That
  section documents the dev/test *analysis* stack; `stream_data`, `bandit` and
  `mix_audit` are likewise not listed. A test-only decoder does not belong there.
